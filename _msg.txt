Rebuild the world as one scalable scene, and make the layout fluid

New background, and a different way of building it. The scene — scalloped
hills, outlined slime blocks, two character clusters, chain coins and clouds —
is now ONE inline SVG in a single 1536x520 coordinate space, generated by
tools/build-scene.mjs.

That is the part worth keeping. The old version was an SVG for the hills plus
absolutely-positioned HTML for the mascots, clouds and coins, and those two
halves are sized by different rules: they lined up at one viewport width and
drifted everywhere else, which is why the props kept landing on a character's
face. Inside one viewBox with preserveAspectRatio="xMidYMax slice" the browser
scales the whole illustration as a unit, so the alignment is correct at every
resolution by construction rather than by tuning. Nothing in .world is
positioned HTML any more, and a test now asserts that.

The hills are scalloped instead of smooth: a row of circles centred on the
profile line plus a polygon through the same centres. The circles carry no
stroke, so overlapping them unions for free — that is the whole reason this is
circles rather than one hand-authored outline. The profile stays a valley, high
at the shoulders and dipping through the middle, which is what keeps the footer
on paper instead of on green.

The blocks are the one part of the scenery that carries the die line, and their
three faces are a deliberately wide value spread. A cube whose faces are near
neighbours reads as a flat tile however good the outline is. A first pass had a
gloss diamond inset on each top face; it read as a chipped facet, so it is gone.

The cast is four characters per corner rather than one mascot with a prop. MUMU
was tried and dropped: it is a tight head-crop that bleeds off all four edges,
so at corner size it is an orange slab, not a character. Measured edge alpha
across all 52 pieces to pick the rest rather than guessing from thumbnails.

Layout is fluid now. --page, both rails, the gaps and the padding are clamps
instead of fixed pixels, and the body size scales with the viewport: 15px on a
2560px monitor is a different reading distance from 15px on a laptop, and a
fixed body size is what made a big screen look like a small screen with
margins. tools/sweep.mjs renders twelve real viewport sizes from 360x780 to
2560x1440 and fails on horizontal overflow, clipped cards or console errors.
All twelve are clean. Two things it caught: at tablet width the wordmark's .9
line-height put its ascenders inside the button row, and the mode counter was
spanning to a second full-width row, which reads as a progress bar rather than
a score.

One pre-existing defect surfaced, not caused by this change. Blur draws the
logo into a 150px frame and wants ~292px for a crisp 2x reveal; seventeen of
the 105 coins have no source art that big. tools/upsize-logos.js recovered one
($IF) and correctly refused the rest — the DexScreener candidates are different
projects' artwork, which its image comparison is there to catch. Asserting this
against whatever coin the calendar serves made the suite fail about one day in
six for a reason no code change could fix, so the check now names the sixteen
known-low-res tickers: deterministic, still red if any coin outside that list
regresses, and the list is meant to shrink.

84 passing, no console errors.
